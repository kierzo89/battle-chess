# Bounded setup-state segment-access probes

The faithful `src/pending/setup_state_7c99.c` remains unmatched: target141 bytes,
MSC5.00 `/AS /Gs /Os /Zi`142 bytes. The specific access emits a DX:AX far
pointer followed by ES:BX addressing; the original directly loads ES from
DS:4DA6 and compares byte ES:0000. Its zero branch also stores an immediate
zero rather than reusing AX, which follows from the different access sequence.

[Retained probes](../evidence/setup_segment_probes.json) vary only the segmented
access expression: shift, multiplication by65536, addition of zero, bitwise OR
zero and a far structure member. All tested C5 optimized forms produce the
same access sequence and142-byte body. C4's corresponding shifted form emits
148 bytes. Separate diagnostic local-pointer and union forms allocate stack
storage and use LES, so they do not explain the original access. C5 bare
default `/AS /Gs /Zi` emits156 bytes and does not fix the access sequence.

A based pointer would naturally express a fixed offset in a changing segment,
but Microsoft's own [C6 programming manual](https://www.pcjs.org/documents/books/mspl13/c/cadvprg/)
introduces based pointers as new in version6.0. This is a constraint on a possible
source explanation, not evidence that the original used C6. The current C5
reconstruction baseline and the desired exact source shape remain unchanged.
No match or source-generated byte credit is claimed for these probes.

A subsequent retained [flag/release matrix](../evidence/setup_segment_flags.json)
confirms the actual unchanged source also emits142 bytes under MSC5.10 `/Os`
and156 under MSC5.10 bare default, matching the corresponding C5.00 negatives.
C5.00 `/O`, `/Ot`, and `/Ox` each emit144 bytes with the same wrong segmented
access and additional alignment differences. No C6 tools were installed.
