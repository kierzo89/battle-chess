# REA MCP follow-up

All analysis used REA MCP with its Ghidra provider on the same hash-pinned
CHESS.EXE. REA addresses are image offsets +0x10000 in this load profile.
The checker now validates each matching unit's extent against the retained REA
dossier, including executable digest, load segment, language and complete body
ranges. This prevents a changed manifest size from silently truncating a match.

All nine now rebuild to their exact original bytes; they remain assembly
matches. The REA tool returns pseudocode as well as assembly, but autogenerated
C does not receive C matching credit.

The stack helper consumes its return address into CX and subtracts AX from the
post-pop SP. An unsigned borrow or a result below DS:4A00 enters the error path,
which clears AX and jumps to EB2A. Otherwise it installs the new SP and jumps
back through CX. Original-byte Unicorn tests cover ordinary allocation,
equality with the limit, one byte below the limit, and subtraction wraparound.
This supports the stack-check interpretation; it does not identify the exact
compiler release or establish the semantics of the downstream error handler.

## Inventory reconciliation

The saved REA/Ghidra list has 386 candidates; the legacy r2 list has 371.
Their image entry offsets agree at 327 locations; 44 appear only in r2 and 59
only in Ghidra. The union has 430 *candidate entry locations*, not 430 proven
functions. `build/analysis_candidates.csv` records all locations without
discarding either analysis. Missing entries and false positives still require
control-flow and data-boundary review. No whole-game percentage is inferred.

## Decoder-text discrepancy

At REA address 0x1E04D, both `analyze_function` and
`inspect_native_instruction` report `MOV AX,ES`, while the latter also reports
original bytes `8ec0`. Those bytes encode `MOV ES,AX`.
[The exact instruction evidence](../evidence/rea_frame_instruction.json) has ID
`ev_47991e00f101de0878a200f5c9d1e4f7616481f8d76acd6b3cbeda9bdebba160`.
Execution of the original two bytes in Unicorn confirms ES receives AX and AX
stays unchanged. The reconstruction uses `mov es,ax` and matches the original
bytes. This is a concrete reason to corroborate decompiler/disassembly text
before accepting it as recovered semantics.

## Compiler evidence remains bounded

[REA string search](../evidence/rea_compiler_strings.json),
`ev_d309bc65cb95c2c56ab3abd7a14b0fddaa3fd5b3d1f6e30d9ad3c5603651d4eb`,
finds the R6000/R6003/R6009/R6002/R6001 diagnostics in Ghidra's recognized string
inventory. It does not return the Microsoft copyright string previously found
directly in the file. This is a limit of recognized-string coverage, not evidence
that the file lacks the string. Microsoft C runtime provenance is supported;
the exact compiler, linker and flags remain unresolved.
